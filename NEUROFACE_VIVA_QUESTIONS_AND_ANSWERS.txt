Q1. What is the core problem that NeuroFace solves?
Ans:
Traditional attendance systems in academic institutions rely on paper roll-calls,
RFID proximity cards, or fingerprint biometrics. These suffer from significant
drawbacks:
1. Paper attendance consumes 10-15 minutes of lecture time and is prone to
   proxy attendance.
2. RFID cards can be shared with friends ("buddy punching").
3. Fingerprint biometrics cause physical bottleneck queues at classroom doors
   and raise hygiene concerns.
NeuroFace solves this by providing non-intrusive, automated, real-time facial
recognition attendance using classroom webcams/CCTV feeds, combined with strict
anti-spoofing presentation attack detection, OCR-based leave document processing,
and automated medical waiver attendance recalculation.


Q2. Explain the high-level system architecture of NeuroFace.
Ans:
NeuroFace follows a modern decoupled client-server architecture:
1. Client Layer (Frontend):
   - Single Page Application (SPA) built using React 19, Vite, and Tailwind CSS.
   - Captures classroom video via HTML5 MediaDevices / WebRTC and streams sampled
     frames (base64 JPEG) to the backend every 1.2 seconds.
   - Renders live colored bounding boxes (Green=Matched, Amber=Verifying,
     Rose=Phone/Screen Spoof, Red=Unregistered Face) on an HTML5 canvas overlay.
2. Server Layer (Backend):
   - High-performance asynchronous REST API built with FastAPI (ASGI, Uvicorn).
   - Modular layers: API Routing, Schemas (Pydantic v2), Business Logic/Services,
     and Deep Learning AI Pipeline.
3. AI/Computer Vision Engine:
   - MTCNN for multi-stage face detection and 5-point landmark extraction.
   - ArcFace (ResNet backbone) for generating 512-dimensional face embeddings.
   - Custom Multi-Signal Anti-Spoofing engine (Contour, Hough lines, Glare, FFT Moiré).
   - MultiFrameConfirmationBuffer with temporal anti-spoof lockout.
4. Optical Character Recognition (OCR) Engine:
   - Tesseract OCR with regex heuristics extracting leave duration (Half/Full Day),
     applicable subjects, session (FN/AN), and dates.
5. Persistence Layer:
   - SQLAlchemy ORM with SQLite (development) or PostgreSQL (production),
     storing users, academic schedules, face embeddings, attendance records,
     and immutable audit trails.


Q3. Walk through the complete lifecycle of an attendance session.
Ans:
1. Session Initialization: A teacher selects their assigned Course, Class, and
   Time Slot, and clicks "Start Session". An AttendanceSession record is created
   with status ACTIVE.
2. Frame Capture & Streaming: The teacher starts the classroom camera. The frontend
   grabs frames every 1.2s and sends a POST request with the base64 image to
   /api/v1/attendance/sessions/{id}/process-frame.
3. Face Detection & Anti-Spoofing:
   - MTCNN locates all face bounding boxes and 5 facial landmarks.
   - Anti-spoofing engine checks each face for phone screens, bezels, glare,
     and unnatural color flatness.
4. Feature Extraction & Matching:
   - Good quality live faces are passed to ArcFace to extract a 512-D vector.
   - Cosine similarity is computed against pre-registered embeddings of students
     enrolled in that class.
5. Multi-Frame Confirmation:
   - A student must be positively recognized in 3 clean frames before attendance
     is officially committed to the database.
6. Record Persistence: An AttendanceRecord (PRESENT, confidence score, timestamp)
   is written to SQLite/PostgreSQL.
7. Finalization: When the teacher clicks "Finish Session" (or time expires),
   all unverified enrolled students are automatically marked ABSENT.


Q4. How are roles structured in NeuroFace? What is the academic hierarchy?
Ans:
NeuroFace enforces Role-Based Access Control (RBAC) across three principal user roles:
1. ADMIN: Full system governance; manages academic master data (departments,
   regulations, classes, subjects, slots, course assignments), manages teacher
   profiles, fine rules, and system-wide audit logs.
2. TEACHER / HOD:
   - Teachers can start live attendance sessions for assigned classes, view live
     telemetry, override records, review reports, and take attendance reports.
   - Teachers designated as HOD (Head of Department) or Class Advisor have elevated
     privileges to review and approve student face registrations, face re-registrations,
     and student leave/medical waiver applications.
3. STUDENT: Can view personal attendance percentages per course, apply for leaves
   with medical certificates, and register/re-register their face biometric.


Q5. What happens when a student registers or re-registers their face?
Ans:
To prevent unauthorized biometric tampering:
1. When a student registers or updates their face, the system captures 3 distinct
   facial angles, verifies face quality (blur, illumination, resolution), extracts
   512-D ArcFace vectors, and stores them with face_registered = FALSE.
2. An ApprovalRequest entry is automatically generated with type FACE_REGISTRATION
   or FACE_REREGISTRATION and status PENDING_APPROVAL.
3. The student's facial embeddings remain INACTIVE and cannot be matched in live
   classroom sessions until an authorized Admin, HOD, or Class Advisor reviews
   and clicks "Approve".

3. Automatic Data Validation: Utilizes Pydantic v2 for automatic request parsing,

4. Auto-Generated Interactive Documentation: Produces OpenAPI (Swagger UI) at /docs

Q7. What database ORM is used and how does it maintain data integrity?
Ans:
SQLAlchemy 2.0 ORM is used. Data integrity is maintained via:
1. Foreign Key Constraints with cascading policies (e.g., student linked to class,
   attendance records linked to sessions and students).
2. Unique Constraints: Preventing duplicate attendance records for the same student
   in the same session (session_id + student_id).
3. Enum Fields: Restricting statuses (AttendanceStatus: PRESENT, ABSENT, MEDICAL_LEAVE,
   EXCUSED; ApprovalStatus: PENDING, APPROVED, REJECTED).
4. Atomic Transactions: Using db.commit() and automatic rollback on exceptions
   to prevent orphan or corrupted records.

SECTION 2: COMPUTER VISION & DEEP LEARNING FACE PIPELINE

Q8. What deep learning model is used for face detection, and why?
Ans:
Multi-task Cascaded Convolutional Networks (MTCNN) is used.
It was selected over Haar Cascades and standard HOG-SVM because:
1. Invariance: Robust against variations in lighting, facial expressions, and
   moderate head rotations (yaw, pitch, roll).
2. Joint Task Learning: Simultaneously outputs the face bounding box and 5 facial
   landmarks (left eye, right eye, nose tip, left mouth corner, right mouth corner).
3. High Precision: Has an extremely low false-positive rate compared to Haar cascades,
   preventing background clutter from being mistaken for human faces.


Q9. Explain the three stages of the MTCNN architecture.
Ans:
MTCNN consists of three cascaded convolutional networks:
1. P-Net (Proposal Network):
   - A fully convolutional network (FCN).
   - Scans an image pyramid across multiple scales to generate candidate bounding
     boxes and their calibration vectors.
   - Uses Non-Maximum Suppression (NMS) to merge highly overlapping bounding boxes.
2. R-Net (Refine Network):
   - A standard CNN that takes candidate crops from P-Net.
   - Rejects a large number of false positive bounding boxes.
   - Performs further bounding box regression and NMS.
3. O-Net (Output Network):
   - A deeper CNN that takes remaining candidates from R-Net.
   - Refines bounding boxes with higher thresholding.
   - Predicts the 5 facial landmark coordinates (eyes, nose, mouth corners).


Q10. What is facial alignment and why is it mandatory before feature extraction?
Ans:
Facial alignment transforms the cropped face so that the eyes lie on a horizontal
line and the facial features are centered at canonical coordinates.
Without alignment, two images of the exact same student—one looking straight and
one with head tilted at 20 degrees—would produce substantially different feature
vectors in the CNN.
In NeuroFace:
1. The angle between the two eyes is calculated: theta = arctan(dy / dx).
2. An affine transformation matrix is computed using cv2.getRotationMatrix2D centered
   between the eyes.
3. The image is rotated and scaled so that both eyes align horizontally at fixed
   proportional positions, ensuring scale and rotation invariance.


Q11. What model is used for face recognition / feature representation?
Ans:
ArcFace (Additive Angular Margin Loss for Deep Face Recognition) with a Deep
ResNet-50 / ResNet-100 backbone.
ArcFace takes the 112x112 aligned face crop and outputs a 512-dimensional continuous
feature embedding vector:
   e = f(face_crop) in R^512
The vector is L2-normalized so that ||e||_2 = 1.0 (it lies on the surface of a
512-dimensional unit hypersphere).


Q12. What is ArcFace (Additive Angular Margin Loss) and why is it superior to
     standard Softmax or Triplet Loss?
Ans:
1. Traditional Softmax Loss optimizes separable features but does not enforce a
   sufficiently high margin between classes, making it inadequate for open-set
   face recognition.
2. Triplet Loss requires combinatorial triplet mining (Anchor, Positive, Negative),
   which is computationally expensive, unstable to train, and converges slowly.
3. ArcFace introduces an Additive Angular Margin penalty 'm' directly into the
   angular space:
      L_arc = - log [ exp(s * cos(theta_y + m)) /
             ( exp(s * cos(theta_y + m)) + sum_{j != y} exp(s * cos(theta_j)) ) ]
   where:
   - theta is the angle between the weight vector W and feature x.
   - s is the feature scale radius.
   - m is the angular margin (typically 0.5 radians).
By penalizing the geodesic distance on the hypersphere, ArcFace simultaneously
enforces intra-class compactness (faces of the same person are pushed closer)
and inter-class discrepancy (faces of different persons are pushed far apart).


Q13. How does NeuroFace compute similarity between two face embeddings?
Ans:
Because ArcFace embeddings are L2-normalized (unit norm ||A|| = ||B|| = 1.0),
the Cosine Similarity is equal to the simple Dot Product:
   Cosine_Similarity(A, B) = (A . B) / (||A|| * ||B||) = A . B = sum_{i=1}^{512} (A_i * B_i)
Cosine similarity ranges between -1.0 and +1.0:
- +1.0 represents identical feature representations.
- 0.0 indicates orthogonal (completely unrelated) representations.
- Values >= 0.50 indicate the same individual under varying lighting/angles.


Q14. What threshold is used for face matching in NeuroFace and why?
Ans:
NeuroFace enforces a cosine similarity matching threshold of 0.50 (with 0.70+
representing very high confidence matches).
- If max_similarity >= 0.50: The student is classified as MATCHED.
- If max_similarity < 0.50: The face is classified as UNKNOWN (unregistered person).
This threshold was empirically calibrated to ensure:
- False Acceptance Rate (FAR) < 0.01% (an unauthorized or unregistered person
  is virtually never mistaken for an enrolled student).
- False Rejection Rate (FRR) < 1.5% under standard indoor classroom illumination.


Q15. What image quality checks are performed before passing a face to ArcFace?
Ans:
In backend/app/ai/quality.py, evaluate_face_quality performs three checks:
1. Blur Detection (Laplacian Variance):
   cv2.Laplacian(gray_crop, cv2.CV_64F).var() computes the second spatial derivative.
   Sharp edges produce high variance; blurry faces produce low variance.
   Threshold: Variance must be >= 65.0.
2. Illumination / Exposure Check:
   Mean pixel intensity of the grayscale crop must lie within [45, 220].
   Faces in severe underexposure (< 45) or blown-out glare (> 220) are rejected.
3. Minimum Resolution:
   The face bounding box must be at least 55x55 pixels. Distant, tiny pixelated
   faces are skipped to avoid garbage embeddings.


Q16. What is the time complexity of matching a face against a class of 60 students?
Ans:
Let N be the number of enrolled embeddings in the class pool (e.g., 60 students * 3
embeddings each = 180 vectors of size 512).
Matrix multiplication between query vector Q (1 x 512) and Pool matrix P (180 x 512):
   Similarities = Q * P^T
Time Complexity: O(N * D) where D = 512.
For N = 180, this requires approximately 92,160 floating point operations (FLOPs),
which executes in under 0.25 milliseconds using NumPy vectorized BLAS (Intel MKL/OpenBLAS).
Hence, 1-to-N matching is exceptionally fast and does not bottleneck the camera loop.

SECTION 3: ANTI-SPOOFING, LIVENESS & PRESENTATION ATTACK DETECTION
================================================================================

Q17. What is a Presentation Attack (Spoofing) in facial recognition systems?
Ans:
A Presentation Attack occurs when an adversary presents a biometric fake or
artifact to the camera instead of their live physical face.
Common forms:
1. Photo Attack: Holding a printed 2D photograph of a registered student.
2. Screen/Replay Attack: Holding a smartphone, tablet, or laptop displaying a
   high-resolution photo or recorded video of the student.
3. 3D Mask Attack: Wearing a sculpted silicone or plastic face mask.
4. Non-Face Object Artifacts: Backdrops, bag prints, or posters triggering false
   positive face detections.


Q18. Describe the multi-signal anti-spoofing architecture in NeuroFace.
Ans:
NeuroFace implements a multi-layer defense in backend/app/ai/anti_spoof.py:
1. Anatomical Facial Landmark Geometry Verification
2. Human Skin Chrominance Verification in YCrCb Color Space
3. Phone Quadrilateral Chassis Contour Detection
4. Screen Bezel & Chassis Hough Line Detection
5. Planar Screen Glass Specular Glare Detection
6. 2D Fast Fourier Transform (FFT) Display Subpixel Moiré Analysis
7. Color Gamut Flatness & Dynamic Range Standard Deviation Check
8. Multi-Frame Temporal Confirmation Buffer with Active Spoof Lockout


Q19. How does Anatomical Landmark Geometry Verification reject non-face objects?
Ans:
When MTCNN mistakenly detects a pattern on a backpack, clothing, or wallpaper,
verify_face_landmarks inspects the 5 facial landmarks:
1. Eye Horizontal Separation: Distance between left and right eyes must be >= 0.16 * width.
2. Vertical Ordering: Eyes must be strictly above the nose, and nose must be strictly
   above the mouth:
      eyes_y < nose_y < mouth_y
3. Facial Proportions: Vertical eye-to-mouth distance must lie between 20% and 85%
   of the bounding box height.
4. Nose Centering: Horizontal coordinate of the nose must fall within the eye boundaries.
Scrambled or inverted patterns immediately fail and are flagged as NON_FACE_OBJECT.


Q20. How does Skin Chrominance Verification in YCrCb color space work?
Ans:
In RGB/BGR color space, skin tone is heavily correlated with luminance (brightness).
NeuroFace converts the face crop to the YCrCb color space, which decouples luminance (Y)
from chrominance (Cr = Red-difference, Cb = Blue-difference).
Across all human ethnicities (fair, olive, brown, dark):
- Cr consistently clusters between 130 and 178.
- Cb consistently clusters between 75 and 138.
The system calculates the ratio of pixels matching this envelope across the central
60% of the face. If skin_ratio < 0.28, the object is rejected as NON_FACE_OBJECT.


Q21. How does NeuroFace detect if a face is being presented on a smartphone?
Ans:
When a phone is held in front of the camera, five distinct physical signatures appear:
1. Quadrilateral Chassis Detection (cv2.approxPolyDP):
   In the padded context surrounding the face (pad_x = 0.45 * bw), the system runs
   Canny edge detection and contour approximation. A smartphone chassis presents
   a 4-corner polygon (quadrilateral) with an aspect ratio between 1.25 and 2.40.
2. Straight Bezel Lines (cv2.HoughLinesP):
   Phone edges produce long, perfectly straight horizontal and vertical lines.
   If >= 2 vertical, >= 2 horizontal, or 1 horizontal + 1 vertical lines are found
   enclosing the face, a score of +0.55 is added.
3. Planar Glass Glare:
   Phone glass displays specular reflections with near-zero saturation and maximum
   brightness (V >= 242, S < 45 in HSV). Glare ratio > 0.025 adds +0.35.
4. Moiré High-Frequency Patterns (2D FFT):
   Camera sensors capturing an electronic screen create subpixel interference (moiré).
   A 2D Fast Fourier Transform analyzes the magnitude spectrum in the high-frequency
   band (radius 42-62). High-frequency ratio > 0.55 adds +0.30.
5. Flat Dynamic Range:
   Photos on screens lack true 3D skin lighting gradients. Average standard deviation
   across channels < 11.5 adds +0.25.
If total spoof_score >= 0.45, the face is rejected with status SPOOF_DETECTED.


Q22. What was the critical bug where a phone was detected but attendance was
     still marked PRESENT, and how did you resolve it?
Ans:
Root Cause:
1. When a phone was held to the camera, some frames detected the phone bezel/glare
   and flagged it as SPOOF_DETECTED, but previous frames where the phone was tilted
   or glare was absent had already matched the face and stored hits in the tracker.
2. The tracker previously required only 2 hits across an 8-second window and NEVER
   purged its buffer when a spoof occurred.
3. In attendance.py, when spoof occurred, it simply called `continue` for that face,
   leaving other accumulated hits intact in memory.
Resolution:
1. Implemented Active Spoof Lockout in tracker.py:
   Added record_spoof(session_id, lockout_seconds=4.0).
   When a spoof is detected, the confirmation buffer for the entire session is
   IMMEDIATELY WIPED, and a 4.0-second lockout timer is activated.
2. Added is_locked_out(session_id):
   During the 4-second lockout window, record_hit strictly returns FALSE and drops
   all hits.
3. Implemented Two-Pass Frame Evaluation in attendance.py:
   - Pass 1 evaluates authenticity across all faces in the camera scene.
   - If ANY face in the scene is a SPOOF_DETECTED, the entire session is locked out
     instantly.
   - Pass 2 rejects all faces if the session is locked out.
4. Increased required hits:
   Raised required consecutive clean frames from 2 to 3 (window_size=4, max_idle=4.0s).


Q23. Why is temporal multi-frame confirmation necessary in facial recognition?
Ans:
In single-frame recognition, a momentary false positive (e.g., motion blur, a photo
shown for 0.1s, or optical noise) could instantly mark a student PRESENT.
Temporal confirmation requires the student's face to be consistently detected,
unspoofed, and matched across 3 consecutive frames (spanning ~3.6 seconds of physical
presence). This eliminates 99.9% of transient glitches and presentation attacks.


Q24. Can an attacker bypass the system using a video of a student blinking?
Ans:
No. Even if the video shows natural blinking and head movement:
1. The phone chassis / bezel edges surrounding the face are still detected by
   detect_phone_quadrilateral and HoughLinesP.
2. The subpixel moiré interference grid from the phone LCD/OLED panel remains present
   and is captured by the 2D FFT analyzer.
3. The glass specular reflection remains detectable in HSV space.
4. As soon as any single frame triggers SPOOF_DETECTED, the 4-second lockout timer
   activates and wipes all confirmation hits, preventing attendance from ever reaching 3 hits.


Q25. How does the system handle real human faces without triggering false spoof alarms?
Ans:
Real human faces in typical classroom environments:
1. Have organic, curved contours (hair, ears, jawline, neck) with no rigid 4-point
   rectangular chassis.
2. Produce smooth spatial gradients rather than high-frequency electronic moiré spikes.
3. Have natural skin diffusion with dynamic range standard deviation > 20.0.
4. Display natural skin chrominance in YCrCb.
Consequently, genuine human faces produce a spoof_score of 0.0 to 0.15, well below
the 0.45 rejection threshold.

SECTION 4: OPTICAL CHARACTER RECOGNITION (OCR) & LEAVE WORKFLOWS

Q26. What is the role of OCR in NeuroFace?
Ans:
When students are sick or require personal leave, they upload a photo or scan of
their handwritten/printed leave letter or doctor's medical certificate.
Instead of requiring teachers to manually re-type dates, reasons, and applicable courses,
NeuroFace uses Tesseract OCR to automatically parse the document, extract key metadata,
and populate the leave application form for one-click submission.


Q27. How does the OCR pipeline extract structured data from unstructured text?
Ans:
In backend/app/services/ocr_service.py:
1. Image Preprocessing:
   PIL opens the image, converts to RGB, and passes it to pytesseract.image_to_string.
2. Date Extraction:
   A comprehensive regex scans for Indian and International date patterns:
   - DD-MM-YYYY, DD/MM/YYYY, DD.MM.YYYY, YYYY-MM-DD
   - Ordinal numbers: "1st November 2026", "23rd Oct 2026"
   A parser helper parse_date_to_iso standardizes all matched strings into ISO YYYY-MM-DD.
3. Duration Classification:
   Detects whether the leave is FULL_DAY or HALF_DAY, and identifies session (FN vs AN).
4. Subject Extraction:
   Scans the text against the student's enrolled courses (codes and names) to identify
   if the leave applies to a specific lecture period.
5. Reason Classification:
   Categorizes keywords: "fever", "hospital", "illness" -> MEDICAL; "wedding",
   "family function", "personal" -> CASUAL / OD.


Q28. How does the OCR service differentiate between Full-Day and Half-Day leaves?
Ans:
The function extract_leave_metadata utilizes prioritized keyword matching:
1. Half-Day Detection:
   Matches keywords such as "half day", "half-day", "forenoon", "afternoon", "fn",
   "an", "first half", "second half", "morning session", "afternoon session".
   If found, detected_day_type is set to HALF_DAY.
2. Session Assignment:
   - If "forenoon", "morning", or "fn" appears: detected_half_day_session = "FN"
   - If "afternoon", "post lunch", or "an" appears: detected_half_day_session = "AN"
   - Otherwise: detected_half_day_session = "GENERAL"
3. Full-Day Detection:
   If no half-day markers exist, or if multi-day spans ("from ... to ...") are found,
   detected_day_type defaults to FULL_DAY.


Q29. How does OCR link a leave letter to a specific subject?
Ans:
1. When calling /api/v1/leaves/ocr-preview, the backend fetches the student's
   enrolled subjects from academic assignments.
2. The OCR service matches both the course codes (e.g., "CS301", "MA201") and course
   titles (e.g., "Neural Networks", "Database Systems") against the raw extracted text.
3. If a match is found:
   - detected_subject_id, detected_subject_name, and detected_subject_code are set.
   - For half-day or single-period leaves, the leave is applied specifically to that course.
   - For full-day general leaves, the leave applies across all scheduled courses for that day.


Q30. What fallback mechanism exists if Tesseract OCR is not installed or encounters
     low-quality handwriting?
Ans:
The system implements a graceful fallback:
1. In get_tesseract_path(), the system searches standard Windows installation paths
   (C:\Program Files\Tesseract-OCR\tesseract.exe, AppData, and system PATH).
2. If the binary is missing or the image is illegible, the OCR endpoint returns a
   graceful response with confidence = 0.0 and detected_scope_note = "No readable text detected".
3. The frontend displays the uploaded image alongside editable input fields, allowing
   the student to verify, adjust, or manually fill the extracted dates and reasons
   before submission.


Q31. Explain the multi-tier approval workflow for Leave Applications.
Ans:
1. Submission: Student uploads letter -> OCR pre-fills data -> Student submits ->
   LeaveRequest created with status PENDING.
2. Advisor Review: The student's assigned Class Advisor receives the leave request on
   their dashboard. The advisor can review the attached image, OCR confidence, and notes.
3. HOD Final Oversight: For medical leaves exceeding 3 days or institutional OD (On-Duty),
   the Head of Department (HOD) provides final approval.
4. Audit Trail: Every approval/rejection event logs user ID, timestamp, and review
   comments into the AuditLog table.


Q32. How do approved medical leaves impact a student's attendance percentage?
Ans:
Under university regulations (e.g., AICTE / Anna University / UGC norms):
- Minimum required attendance is typically 75%.
- Students with 65% - 74% attendance face condonation fines or semester detention
  unless they have an approved Medical Waiver.
When an Admin or HOD approves a Medical Waiver in NeuroFace:
1. The student's medical leave days are credited to the waiver pool.
2. The effective attendance percentage is recalculated:
      Effective_% = (Present_Sessions + Approved_Medical_Sessions) / Total_Conducted_Sessions * 100
3. This lifts the student above the detention threshold and automatically waives
   the low-attendance penalty fine.


Q33. What is the difference between a Leave Request and an Attendance Record?
Ans:
- AttendanceRecord: An actual session-level entry recorded during a scheduled classroom
  hour by the live camera or teacher override (Status: PRESENT or ABSENT).
- LeaveRequest: A student-initiated document-supported application for absence covering
  a specific date or date range. Once approved, it serves as the official justification
  for absence and enables attendance condonation.

Q34. How is user authentication and session security implemented?
Ans:
1. Password Storage: Passwords are never stored in plaintext. They are hashed using
   bcrypt with a randomized 12-round salt via passlib.context.CryptContext.
2. Token Standard: JSON Web Tokens (JWT) signed with HMAC-SHA256 (HS256).
3. Token Lifecycle:
   - Upon successful login at /api/v1/auth/login, a signed JWT token containing
     user_id, email, and role is returned.
   - The token expires after 1440 minutes (24 hours).
4. Protected Endpoints: FastAPI Dependency Injection (Depends(get_current_user))
   extracts the Bearer token from the HTTP Authorization header, verifies signature
   and expiration, and injects the authenticated User object into the route handler.


Q35. Explain how Role Guards (get_current_teacher, get_current_admin) operate in FastAPI.
Ans:
FastAPI's dependency injection system allows composable security guards:
- get_current_user: Validates the JWT and loads the User model from the database.
- get_current_teacher: Calls get_current_user and verifies that user.role in ["TEACHER", "ADMIN"].
  If unauthorized, it raises an HTTPException(status_code=403, detail="Forbidden").
- get_current_admin: Verifies user.role == "ADMIN".
This guarantees that student users cannot access teacher camera sessions or admin setups.


Q36. Explain the database schema design and key relationships.
Ans:
The schema consists of 11 relational tables:
1. User: Credentials, role (ADMIN, TEACHER, STUDENT), active status.
2. TeacherProfile: Department, employee ID, is_hod flag, is_advisor flag.
3. Student: Register number, roll number, class_id, face_registered flag.
4. FaceEmbedding: 512-D vector (JSON serialized), student_id, embedding_number (1, 2, 3).
5. AcademicClass: Batch, department, semester, section.
6. Subject: Course code, course name, credits, semester.
7. CourseAssignment: Maps Teacher + Subject + AcademicClass.
8. AttendanceSession: CourseAssignment_id, teacher_id, date, start_time, end_time, status.
9. AttendanceRecord: session_id, student_id, status, confidence_score, marked_by.
10. LeaveRequest: student_id, dates, reason, day_type, session, document_path, approval_status.
11. AuditLog: User action tracking (timestamp, action, entity, JSON details).


Q37. How are 512-dimensional face embeddings stored in the database?
Ans:
In the FaceEmbedding model:
- The vector is stored as a JSON string: json.dumps(embedding.tolist()).
- When the live attendance session begins, all registered vectors for students of
  that class are loaded into memory and converted back to a contiguous float32 NumPy
  array: np.array(json.loads(row.embedding_vector), dtype=np.float32).
- This provides cross-database compatibility across SQLite and PostgreSQL without
  requiring specialized vector extensions like pgvector for small-to-medium class sizes.


Q38. What are Pydantic schemas and how do they differ from SQLAlchemy models?
Ans:
- SQLAlchemy Models: Define the database schema, relational constraints, foreign keys,
  and handle persistence/queries with the SQL database engine.
- Pydantic Schemas (Models): Define data validation and serialization contracts for
  API requests and responses. They enforce field types, handle JSON serialization,
  validate input constraints (e.g., email format, string lengths), and prevent internal
  database secrets (like hashed passwords) from leaking into API responses.


Q39. What happens if two teachers start attendance sessions for the same class
     at the same time?
Ans:
The database and business logic enforce slot exclusivity:
1. Each session requires a slot_id (e.g., Period 1: 09:00 - 10:00).
2. The session creation endpoint queries AttendanceSession for any existing ACTIVE
   session matching that class_id and slot_id on session_date.
3. If an active session exists, the endpoint raises HTTPException(400, "An attendance
   session for this class and slot is already active").


Q40. How does NeuroFace prevent database locks during real-time frame processing?
Ans:
1. Short-Lived Database Sessions: The FastAPI Depends(get_db) dependency yields a
   scoped SQLAlchemy session that closes immediately after the request finishes.
2. In-Memory Face Matching: Face embeddings and student IDs are pre-cached in memory
   at the start of the session. During the 1.2-second frame processing loop, matching
   happens entirely in CPU/RAM without querying the database for every face.
3. Conditional DB Writes: AttendanceRecord insertions only occur on the 3rd confirmed
   frame, and only if student_id not in already_marked_ids (a fast Python in-memory set).


Q41. How does the teacher manual record reset endpoint work?
Ans:
If a student was mistakenly marked or needs to be revoked:
1. Route: DELETE /api/v1/attendance/sessions/{id}/records/{record_id}
2. The endpoint deletes the AttendanceRecord from the database.
3. Crucially, it calls frame_tracker.clear_student(session.id, student_id) to wipe
   the memory buffer, preventing the AI camera from immediately re-marking the student
   on the very next frame.
4. An audit event REVOKE_ATTENDANCE_RECORD is recorded.


Q42. How are PDF and Excel attendance reports generated in backend/app/api/v1/reports.py?
Ans:
1. Excel Reports: Built using openpyxl. Formats student registration numbers, names,
   total hours conducted, hours attended, approved medical leaves, and overall percentage
   with colored conditional formatting (Green >= 75%, Red < 75%).
2. PDF Reports: Built using ReportLab. Generates institutional grade tables with
   header logos, subject codes, faculty signatures, and fine calculations.

Q43. What technologies power the NeuroFace frontend?
Ans:
- Core Framework: React 19 Single Page Application (SPA).
- Build Tool: Vite 8.3 (extremely fast Hot Module Replacement and production bundling).
- Styling: Tailwind CSS 3.4 for responsive, utility-first UI styling.

- Icons: Lucide React for consistent modern iconography.
- HTTP Client: Axios with request/response interceptors injecting JWT Bearer headers.


Q44. How does the live camera stream work without overloading the backend server?
Ans:
Instead of sending a heavy 30 FPS raw WebRTC video stream (which would saturate server
bandwidth and CPU):
1. The browser requests access to the webcam via navigator.mediaDevices.getUserMedia.
2. The video is rendered locally in a hidden HTML5 <video> element.
3. A JavaScript setInterval timer fires every 1200ms (1.2 seconds).
4. The timer captures the current frame onto an off-screen HTML5 <canvas>, converts it
   to a compressed JPEG base64 string (canvas.toDataURL('image/jpeg', 0.8)), and sends
   it via Axios to /process-frame.
5. While a frame is awaiting a response, processingRef.current = true prevents overlapping
   requests, ensuring predictable network and CPU usage.


Q45. How does the frontend draw real-time bounding boxes on the camera feed?
Ans:
In LiveAttendancePage.jsx:
1. An HTML5 <canvas> element is positioned directly on top of the <video> element
   with absolute positioning and identical dimensions.
2. When the backend responds with face_results, the canvas context (ctx) clears the
   previous frame (ctx.clearRect).
3. For each face, it scales the coordinates [x1, y1, x2, y2] to the canvas display size:
   - Green (#10b981): MATCHED or ALREADY_MARKED -> Shows student name, roll number, and match percentage.
   - Amber (#f59e0b): CONFIRMING -> Shows "Verifying: Name... [xx%]".
   - Rose (#f43f5e): SPOOF_DETECTED -> Shows "PHONE / SCREEN DETECTED - REJECTED".
   - Red (#ef4444): UNKNOWN -> Shows "UNREGISTERED FACE".
   - Slate (#64748b): LOW_QUALITY -> Shows "Low Quality / Blur".
4. ctx.strokeRect draws the bounding box and ctx.fillText renders the label pill.


Q46. How does RoleGuard protect frontend routes?
Ans:
RoleGuard.jsx wraps protected routes in React Router:
1. Checks AuthContext to see if user is authenticated.
2. If not logged in, redirects to /login.
3. If user.role is not in allowedRoles (e.g., student trying to access /admin or /teacher),
   redirects them to their authorized dashboard.


Q47. How is responsiveness achieved across mobile devices and tablets?
Ans:
1. Viewport Meta: width=device-width, initial-scale=1.0.
2. Tailwind Responsive Utilities: Uses sm:, md:, lg:, and xl: breakpoints.
3. Collapsible Navigation: A mobile drawer with a floating hamburger button and backdrop
   overlay that automatically collapses on smaller screens.
4. Flexible Card Grids: grid grid-cols-1 md:grid-cols-2 lg:grid-cols-4 adapting from
   single-column vertical scroll on smartphones to multi-column layouts on desktops.
5. Touch-friendly Tables: Horizontal scroll wrappers (overflow-x-auto) and responsive card
   views for attendance registers.


Q48. How does the frontend handle token expiration?
Ans:
Axios response interceptors inspect every outgoing and incoming HTTP request:
- If an API returns HTTP 401 Unauthorized, the interceptor clears localStorage
  (removes neuroface_token and neuroface_user) and triggers a redirect to /login
  with an alert message "Your session has expired. Please sign in again."


Q49. Why did you use Vite instead of Create React App (CRA)?
Ans:
- Create React App is deprecated by the React team and relies on Webpack, which takes
  30-60 seconds for cold startup and builds.
- Vite uses native browser ES Modules (ESM) and esbuild (written in Go), enabling
  instant server start (< 300ms) and lightning-fast Hot Module Replacement (HMR).
- Vite produces optimized, tree-shaken production bundles using Rollup.

SECTION 7: SECURITY, PRIVACY & PRODUCTION RELIABILITY
================================================================================

Q50. How does NeuroFace protect student biometric privacy (compliance with DPDP / GDPR)?
Ans:
1. No Raw Image Retention: The system does not permanently store raw webcam capture
   frames. Once processed in RAM, the frame is immediately discarded by Python's
   garbage collector.
2. Irreversible Mathematical Templates: Face representations are stored strictly as
   512-dimensional floating-point vectors (embeddings).
3. Non-Invertibility: It is mathematically impossible to reconstruct the original human
   face photograph from a 512-D ArcFace vector; it is a one-way feature abstraction.
4. Access Isolation: Biometric endpoints require authenticated teacher/admin tokens.


Q51. What measures protect against SQL Injection and Cross-Site Scripting (XSS)?
Ans:
1. SQL Injection Prevention:
   - NeuroFace uses SQLAlchemy ORM parameterized queries exclusively. Raw user input
     is never concatenated into SQL strings.
2. XSS (Cross-Site Scripting) Prevention:
   - React automatically escapes all variables rendered inside JSX expressions before
     inserting them into the DOM.
   - Pydantic v2 sanitizes string inputs at the API gateway layer.


Q52. How does the system defend against Cross-Origin Resource Sharing (CORS) attacks?
Ans:
In backend/app/main.py, FastAPI's CORSMiddleware is configured:
- Explicit allow_origins restricts requests to authorized frontend domains
  (e.g., http://localhost:5173 or the institutional domain).
- Restricts allowable HTTP methods (GET, POST, PUT, DELETE) and headers.


Q53. How is the audit log implemented and why is it legally important?
Ans:
In backend/app/models/audit.py, the AuditLog table records:
- user_id, action, entity_type, entity_id, timestamp, IP/details JSON.
Every critical modification—such as an HOD approving a medical waiver, a teacher
manually revoking an attendance record, or an admin modifying fine rules—creates an
immutable audit entry. This ensures institutional accountability and prevents disputes
over attendance tampering.


Q54. How does the system handle high concurrency with multiple classrooms?
Ans:
1. Asynchronous ASGI Architecture: FastAPI runs under Uvicorn with multiple worker
   processes (uvicorn --workers 4).
2. Stateless API Design: Each frame request is completely self-contained, allowing
   horizontal scaling behind a load balancer (Nginx / HAProxy).
3. Memory Footprint: Each ArcFace vector is only 512 * 4 bytes = 2 KB. Even 5,000
   registered students consume only ~10 MB of RAM.


Q55. What happens if the network connection drops momentarily during a live session?
Ans:
1. The frontend camera loop continues running.
2. If an Axios POST fails due to a network timeout, the catch block logs the error,
   resets processingRef.current = false, and attempts the next frame on the next interval.
3. In-memory session state on the server retains all previously confirmed records.
4. When connectivity resumes, recognition resumes seamlessly without lost records.


Q56. How does NeuroFace prevent brute force password guessing attacks?
Ans:
1. Bcrypt Key Stretching: Bcrypt incorporates a work factor (salt rounds = 12),
   requiring ~300ms per password hash calculation, making offline dictionary attacks
   computationally prohibitive.
2. Rate Limiting: Production deployment uses Nginx / SlowAPI rate limiting to cap
   failed login attempts per IP address.

SECTION 8: EDGE CASES & FUTURE ENHANCEMENTS

Q57. How does the system handle identical twins or siblings with high facial similarity?
Ans:
Identical twins share very similar facial geometry, resulting in cosine similarity
scores around 0.65 - 0.75.
NeuroFace handles this by:
1. Class-Scoped Search Pool: The face matching algorithm does not search the entire
   college database (5,000 students); it strictly searches the students enrolled in
   that specific class (typically 60 students).
2. If twins are enrolled in the same class:
   - High similarity thresholding and multi-angle registration embeddings capture
     subtle differences (blemishes, eye spacing, jawline).
   - The teacher dashboard highlights the match confidence and allows immediate manual
     override if necessary.


Q58. What happens when a student wears spectacles, changes hairstyle, or grows a beard?
Ans:
ArcFace was trained on millions of diverse face images using deep residual networks.
- It learns high-level abstract facial feature topologies (bone structure, inter-ocular
  distance, nose bridge height) rather than superficial surface textures like hair
  or glasses.
- Spex/beard changes typically lower similarity marginally (e.g., from 0.88 to 0.74),
  which remains comfortably above the 0.50 threshold.
- If a student undergoes a drastic transformation, they can submit a Face Re-registration
  request via their dashboard, which requires HOD approval.


Q59. How does the system behave under very low or uneven lighting conditions?
Ans:
1. Face Quality Guard: If average luminance falls below 45, evaluate_face_quality
   flags the crop as LOW_QUALITY and prompts the teacher to adjust lighting.
2. Histogram Equalization: For borderline lighting, contrast enhancement is applied
   in the preprocessing pipeline prior to feature extraction.


Q60. How would you deploy NeuroFace in a real-world campus with 100+ classrooms?
Ans:
1. Edge Deployment Architecture:
   - Deploy low-cost Edge AI devices (NVIDIA Jetson Orin Nano or Raspberry Pi 5 with
     Google Coral TPU) inside each classroom to run MTCNN and ArcFace locally.
   - The edge device sends only the matched student IDs and timestamps to the central
     cloud server, reducing institutional bandwidth consumption to near zero.
2. Central Cloud Server:
   - Hosted on AWS/GCP with Docker containers orchestrated via Kubernetes.
   - Central PostgreSQL database with Redis cache for session states and analytics.


Q61. What future enhancements can be added to NeuroFace?
Ans:
1. 3D Structured Light / Infrared (IR) Depth Sensors: Hardware-level liveness verification
   immune to 2D screen attacks.
2. Automated Parent Notifications: Integrating WhatsApp Business API / Twilio to send
   instant automated absence alerts to parents.
3. Automated Timetable Integration: Syncing automatically with Google Calendar / ERP systems.
4. Student Emotion & Engagement Analytics: Measuring classroom attention and fatigue
   levels via facial expression analysis.


Q62. What are the key limitations of the current implementation?
Ans:
1. Severe Occlusion: Face masks (surgical masks) covering the nose and mouth degrade
   MTCNN landmark extraction and ArcFace embeddings.
2. Extreme Camera Angles: Wide-angle fisheye cameras positioned high in auditorium
   ceilings capture steep downward perspectives requiring specialized geometric rectification.
3. OCR Font Variance: Extremely cursive or degraded handwritten doctor prescriptions
   may have lower OCR confidence compared to printed institutional letters.

SECTION 9: RAPID-FIRE VIVA QUESTIONS & CRISP 1-LINERS

Q63. What is MTCNN?
Ans: Multi-task Cascaded Convolutional Networks, a 3-stage deep learning framework
     for joint face detection and 5-point facial landmark alignment.

Q64. What is ArcFace?
Ans: A state-of-the-art face recognition model that uses Additive Angular Margin
     Loss to maximize inter-class separation and minimize intra-class distance.

Q65. What is the dimension of the face embedding vector?
Ans: 512 dimensions (normalized float32 values lying on a unit hypersphere).

Q66. Which similarity metric is used to compare face embeddings?
Ans: Cosine Similarity (equivalent to the dot product of normalized 512-D vectors).

Q67. What is the face matching threshold in NeuroFace?
Ans: 0.50 (with values above 0.70 indicating high confidence).

Q68. How many consecutive clean frames are required before marking attendance?
Ans: 3 consecutive clean frames within a 4-second temporal window.

Q69. What happens to the confirmation buffer when a phone screen is detected?
Ans: The buffer is immediately wiped clean and the session is locked against
     confirmations for 4.0 seconds.

Q70. What is Moiré pattern and how does NeuroFace detect it?
Ans: An optical interference artifact produced when cameras capture digital displays;
     detected using 2D Fast Fourier Transform (FFT) high-frequency analysis.

Q71. Which color space is used to verify human skin presence and why?
Ans: YCrCb color space, because it isolates skin chrominance (Cr and Cb) from
     lighting luminance (Y).

Q72. What tool is used for Optical Character Recognition?
Ans: Tesseract OCR accessed via the pytesseract Python wrapper.

Q73. What is the difference between a Full-Day and Half-Day leave in the system?
Ans: Full-Day applies to all scheduled courses on that date; Half-Day specifies
     either Forenoon (FN) or Afternoon (AN) and can map to a specific subject period.

Q74. What algorithm hashes user passwords?
Ans: Bcrypt with 12 salt rounds via passlib.

Q75. What token standard secures API requests?
Ans: JSON Web Tokens (JWT) signed with HMAC-SHA256 (HS256).

Q76. Which ASGI framework powers the backend?
Ans: FastAPI running on Uvicorn.

Q77. What frontend library and build tool are used?
Ans: React 19 Single Page Application bundled with Vite.

Q78. How does the camera feed reach the backend?
Ans: The browser samples video frames via HTML5 Canvas every 1.2s and posts base64
     encoded JPEG images to the FastAPI REST endpoint.

Q79. Are raw student photos stored in the database?
Ans: No, only irreversible 512-dimensional mathematical embeddings are stored,
     ensuring complete biometric privacy.

Q80. What role must approve a student's face registration before it can be used?
Ans: An Admin, Head of Department (HOD), or designated Class Advisor.
